PRODUCT REQUIREMENT DOCUMENT ・ 権限（ユーザー）管理

用户与角色权限管理 社内ユーザーの登録・編集・無効化と、ロールによる機能権限の割り当て

为「rabbit 請求管理」后台建立最小可用的访问控制：管理员能在系统内完成人员授权与收回， 每个已登录用户只看到、也只能进入其角色允许的业务模块。

01

背景与目标

当前状态

权限管理下的两个页面目前都是「準備中」占位页：/permissions/users 与 /permissions/roles 只显示说明与返回按钮，没有任何数据与操作。 导航由静态常量驱动，全部 15 个模块对所有已登录用户可见可进； 路由守卫只判断登录态，不判断角色。

依据：features/back-office/SPEC.md（占位页规则、无角色判定、风险与依赖）、 proxy.ts（仅 getSessionCookie 乐观判断）、 components/app/nav-config.ts（静态模块清单）。

问题

  • 授权无处落地。新员工入职、岗位调整、离职时，管理员无法在系统内授予或收回模块访问权，只能依赖外部约定与人工提醒。
  • 越权成本为零。任何社内账号都能直接打开請求承認、計上、マスタ編集等敏感页面；菜单可见性也不反映职责差异。
  • 变更不可追溯。谁在什么时候给了谁什么权限，没有记录，事后无法复盘。

目标

建立一套最小但完整的 RBAC：用户台帐 → 角色 → 模块级权限 → 三层一致的访问判定。完成后应能观察到：

  • 管理员不修改代码、不改配置文件，即可完成「新人授权」「转岗调权」「离职停用」三件事。
  • 没有某模块参照权限的用户，在导航、工作台、直接 URL、接口四个入口都拿不到该模块。
  • 每一次用户与角色权限的变更都有操作者、时间、变更前后差异与理由可查。
  • 误操作可恢复：停用可重新有效化，权限变更可再次编辑回原状，不产生物理删除。
产品判断 本模块只管理授权，不管理认证。密码、MFA、SSO、账号创建与注销仍由外部认证基盘负责； 本系统持有的是「谁在本系统里能做什么」的权限台帐。这样与现有无状态认证架构（Better Auth + 第三方认证 API）保持一致，也避免出现两套密码。
02

范围与边界

P0 — 本轮必须完成

编号能力完成的可见证据
FR-01用户列表、关键词检索、状态与角色筛选、分页能按条件找到目标用户，条件保留在 URL
FR-02新建用户（登录 ID、姓名、邮箱、部门、角色）保存后出现在列表首位，状态为「有効」
FR-03编辑用户资料与角色修改后列表即时反映，登录 ID 不可改
FR-04有效化 / 无效化（含理由与保护规则）状态徽标切换，理由记录在审计中
FR-05角色列表、角色详情、权限矩阵与所属用户能看到每个角色能做什么、影响了多少人
FR-06角色权限编辑（系统管理员角色锁定）保存后受影响用户下次请求即按新权限判定
FR-07导航、路由、接口三层访问控制 + 403 页面无权限用户看不到菜单，直接输入 URL 得到 403
FR-08用户与角色变更的操作审计记录每次变更产生一条不可修改的记录

P1 — 明确延后

P1 ・ 一人多角色 P1 ・ 自定义角色新建 / 删除 P1 ・ CSV 批量导入用户 P1 ・ 审计日志查看页面与导出 P1 ・ 权限变更审批流 P1 ・ 密码重置 / 账号解锁入口 P1 ・ 按店铺的数据范围权限

非目标

  • 不实现认证本身：不做登录、密码策略、MFA、SSO 配置，也不在本系统创建或删除外部认证账号。
  • 不实现组织/部门主数据管理，部门取固定候选值（来源 TBD）。
  • 不做临时授权、有效期、时段限制、IP 限制。
  • 不做用户物理删除；离职一律以「無効」表达，保留历史引用。
  • 本 PRD 不定义接口路径、数据库结构与实现方案。
03

产品模型

3.1　术语与角色

术语定义
ユーザー拥有本系统访问权的社内人员。以登录 ID 唯一标识，持有且仅持有一个角色。
ロール一组模块权限的集合。用户通过角色获得权限，权限不直接挂在用户上。
権限对某个业务模块的「参照」或「更新」能力。P0 只到模块级，不做字段级或店铺级数据范围。
参照可以进入模块、查看列表与详情、使用检索与导出（若该模块提供）。不能改变任何数据。
更新可以执行该模块内的写入操作（新建、编辑、停用、导入、审批等），并隐含参照能力。
システムロール系统预置、不可删除的角色。其中「システム管理者」连权限也不可编辑，用于防止锁死。
操作者当前登录并执行操作的用户。所有写操作以操作者身份记录审计。
監査ログ追加写入、不可修改的操作记录，承载时间、操作者、对象、变更前后与理由。

角色定义（仮案，需业务确认）

P0 预置四个系统角色，覆盖后台的典型职责分工。仮 角色名称、数量与职责边界都需业务方确认后固化。

ロール種別职责与典型使用者关键边界
システム管理者システム 系统导入与运维负责人；管理用户、角色与全部业务模块。 唯一可以进入权限管理的角色；权限不可编辑，防止误操作锁死。
マスタ管理者システム 负责店铺、請求 CD、单价等主数据的维护人员。 可更新マスタ管理；对請求业务只读；看不到权限管理。
請求担当システム 日常請求处理人员：取込、承認、調整、計上。 可更新請求業務管理；マスタ只读，避免业务人员改主数据。
閲覧者システム 管理层、审计或临时需要查看数据的人员。 所有业务模块只读；无任何更新能力；看不到权限管理。

04

功能需求

每个需求按「目的 → 触发 → 处理规则 → 结果 → 异常」描述。界面文案使用日文，与现有系统一致。

FR-01

用户列表与检索

P0 /permissions/users 権限：参照

目的

让管理员在几十到数百人的范围内，用最少操作定位「某个人现在是什么角色、是否有效」。

触发与入口

  • 从顶部导航「権限（ユーザー）管理 → ユーザー管理」、工作台卡片或 /permissions/users 直接进入。
  • 需要该模块的「参照」权限；无权限时按 FR-07 处理（不渲染任何用户数据）。

布局

区域内容
页面标题「ユーザー管理」+ 一句说明「社内ユーザーの登録・編集・無効化を行います。」
工具栏关键词输入框（占位提示：ログインID・氏名・メール）、状態筛选、ロール筛选、「条件をクリア」、右侧「新規登録」。无更新权限时只保留检索与清除。
结果区「全 N 件」计数 + 表格 + 分页。
表格列ログインID / 氏名 / 部署 / ロール / ステータス / 最終ログイン / 更新日時 / 操作。

处理规则

  • 默认显示全部用户，按「更新日時」降序；同值时按登录 ID 升序，保证顺序稳定。
  • 关键词对 登录 ID、氏名、メール 做部分一致匹配，不区分大小写与全半角。仮
  • 状态与角色筛选取交集（AND）；三个条件可同时生效。
  • 条件变化 300ms 后自动检索并回到第 1 页；输入框按 Enter 立即检索。
  • 检索条件同步到 URL 查询参数（q / status / role / page），刷新与浏览器返回后条件保持，链接可分享给同权限的人。
  • 每页 20 件；超过时显示上一页 / 下一页与页码，当前页高亮。
  • 关键词前后空白自动去除；空字符串等同未输入。
  • 状态与角色徽标使用固定映射，不出现原始枚举值（如 active）。

结果与状态变化

只读，不改变任何数据。检索行为本身不写审计日志。

空与异常

  • 结果为 0 件：显示「該当するユーザーがいません」+ 副文案「検索条件を変更してください」+「条件をクリア」按钮；不显示空表格与分页。
  • 加载中：表格区域显示骨架行，工具栏保持可操作。
  • 加载失败：显示「ユーザー一覧の取得に失敗しました」+「再試行」，保留当前筛选条件。
  • 会话失效：跳转登录页并带回跳地址。
FR-02

新建用户

P0 権限：更新

目的

新人入职或新增外部协作人员时，管理员一次填完必要信息即可授予初始访问范围。

触发

用户列表右上「新規登録」。仅拥有「更新」权限的操作者可见、可执行。

表单字段与校验

字段必須校验与提示
ログイン ID必須4〜32 文字、半角英数字与 . _ -；不区分大小写唯一。错误文案：「ログインIDは4〜32文字の半角英数字で入力してください」「このログインIDは既に使用されています」
氏名必須1〜50 文字。空欄時「氏名を入力してください」
メールアドレス必須邮箱格式、不区分大小写唯一。错误文案：「メールアドレスの形式が正しくありません」「このメールアドレスは既に使用されています」
部署任意固定候选下拉，含「未設定」。
ロール必須默认选中「閲覧者」；可选项为全部角色。管理员应能在此看到每个角色的简短说明。

处理规则

  • 新建用户的初始状态固定为「有効」，不在表单中提供状态选择。
  • 客户端先做即时校验，提交时服务端必须重复校验唯一性与格式；以服务端结果为准。
  • 登录 ID 保存后不可修改；表单中明确提示「登録後は変更できません」。
  • 默认初始角色为「閲覧者」，避免误操作给出过高权限。

结果与状态变化

  • 保存成功：弹窗关闭，列表回到第 1 页并刷新，新用户按排序规则出现在顶部；显示「ユーザーを登録しました」。
  • 写入一条审计记录：操作種別「作成」、対象ユーザー、登録内容（登录 ID / 氏名 / 部署 / ロール / 状態）。

取消与异常

  • 点击「キャンセル」、遮罩或 Esc：若有未保存修改，二次确认「入力内容を破棄しますか？」。
  • 唯一性冲突（409）：对应字段下方显示冲突文案，保留其他输入，不关闭弹窗。
  • 校验失败（422）：滚动到第一个错误字段并聚焦。
  • 网络或服务异常：弹窗不关闭，显示「登録に失敗しました。もう一度お試しください」与「再試行」，输入全部保留。
仮定 / TBD 本系统只建立权限台帐，不创建外部认证账号。因此新建用户成功，不等于对方立刻能登录； 若外部认证基盘不存在对应账号，该用户登录时会被拒绝。是否需要在保存前校验外部账号存在、或触发外部开通，属于未决事项（见 Q1）。
FR-03

编辑用户

P0 権限：更新

目的

人员转岗、改名、换邮箱或调整职责时，就地修正资料与角色，不需要新建账号。

触发

列表行操作「編集」。点击行内其他区域不打开弹窗，避免误触。

可编辑范围

  • 可改：氏名、メールアドレス、部署、ロール。
  • 不可改：ログイン ID（只读展示并附说明）、ステータス（走 FR-04）、最終ログイン与更新者（系统字段）。
  • 操作者不能修改自己的角色，防止把自己移出权限管理后再也进不来。该行的角色选择禁用，并提示「自分自身のロールは変更できません」。

处理规则

  • 弹窗预填当前值；校验规则与 FR-02 一致（登录 ID 之外）。
  • 并发保护：以打开弹窗时的「更新日時」为基准做乐观锁。保存时若已被他人修改，返回冲突，弹窗转为只读并提示「他のユーザーが先に更新しました」，提供「最新の内容を読み込む」。
  • 角色变更即时生效：该用户下一次请求即按新角色判定，不要求重新登录。

结果与状态变化

  • 保存成功：列表对应行就地更新并显示「ユーザーを更新しました」。
  • 审计记录按字段记录变更前后值，未变化字段不记录。

异常

  • 无变更直接保存：关闭弹窗，不写审计、不提示成功。
  • 邮箱/登录 ID 冲突：同 FR-02。
  • 保存过程中用户被他人停用：提示「対象ユーザーの状態が変更されています」并刷新该行，不覆盖状态。
FR-04

有效化 / 无效化

P0 敏感操作 権限：更新

目的

离职、长期休假或误建账号时，立即收回访问权，同时保留该用户在历史数据中的引用，可随时恢复。

触发

有效用户行操作显示「無効化」；无效用户显示「有効化」。仅在拥有「更新」权限时出现。

确认弹窗

  • 标题：「このユーザーを無効化しますか？」/「このユーザーを有効化しますか？」
  • 必须展示対象：氏名 + 登录 ID + 当前角色，避免停错人。
  • 影响说明：「無効化すると、このユーザーは次回のリクエストから本システムにアクセスできなくなります。履歴データは削除されません。」
  • 无效化时「理由」必填：退職 / 異動 / 長期休暇 / 誤登録 / その他。选择「その他」时必须填写 1〜200 字说明。
  • 有效化时理由选填。
  • 主按钮为「無効化」（危险样式）/「有効化」；次按钮「キャンセル」。未选择理由时主按钮禁用。

保护规则

场景系统行为
操作者对自己执行无效化禁止。提示「自分自身を無効化することはできません」，不进入确认流程。
目标为最后一个有效的「システム管理者」禁止。提示「システム管理者が0人になるため無効化できません」。先指定另一名管理员再操作。
目标已处于目标状态（并发导致）不报错；刷新该行并提示「既に無効化されています」。
目标不存在或已被移除提示「対象ユーザーが見つかりません」，刷新列表。

结果与状态变化

  • 状态徽标即时切换（有効 ↔ 無効）；显示「ユーザーを無効化しました」/「ユーザーを有効化しました」。
  • 审计记录：操作種別、対象、変更前後の状態、理由、操作者与时间。
  • 无效用户保留在列表中（默认筛选为全部），可被检索到，便于复查与恢复。
  • 有效化后访问权立即恢复；若角色权限在此期间变化，以当前角色为准。
仮定 / TBD 「次回リクエストからアクセス不可」要求服务端在每次请求读取用户当前状态，而不是只信任登录时签发的会话。 现有无状态会话是否支持即时失效、以及失效延迟的可接受上限，需要技术侧确认（见 Q6）。TBD
FR-05

角色列表与详情

P0 /permissions/roles 権限：参照

目的

让管理员一眼看清「这个角色能做什么、现在有多少人拥有它」，作为授权与调权的依据。

布局

  • 页面标题「ロール管理」+ 说明「ロールと権限の割り当てを管理します。」
  • 左侧角色列表：名称、種別徽标、所属用户数；当前选中项高亮。
  • 右侧角色详情：名称、種別、説明、更新日時、权限矩阵（只读）、所属用户预览（最多 5 名 + 「該当ユーザーを表示」）。
  • 有更新权限时，详情右上显示「権限を編集」；无更新权限时不显示。

处理规则

  • 默认选中「システム管理者」。
  • 权限矩阵与 3.2 节完全同源，页面不另行解释权限含义。
  • 「該当ユーザーを表示」跳转 /permissions/users?role=<角色ID>，筛选条件沿用 FR-01。
  • 所属用户数统计包含无效用户；详情中标注「有効 N 名 / 全 M 名」，避免误判影响面。

空与异常

  • 系统角色固定存在，正常不会为 0 件；若读取失败显示「ロール情報の取得に失敗しました」+「再試行」。
  • 角色详情读取失败时，列表保持可用，详情区显示局部错误与重试。
FR-06

角色权限编辑

P0 敏感操作 権限：更新（仅系统管理员）

目的

当职责分工变化时，一次调整即可批量改变该角色下所有人的可用范围，不必逐个改用户。

触发与权限

  • 角色详情「権限を編集」。只有拥有「権限（ユーザー）管理 = 更新」的操作者可执行，默认仅「システム管理者」满足。
  • 「システム管理者」角色整体只读：名称、説明、权限矩阵全部禁用，并显示锁标识与说明「システム管理者の権限は変更できません（ロックアウト防止）」。
  • 其余系统角色的名称与種別不可改，説明与权限可改。

编辑规则

操作结果
勾选某模块「更新」自动同时勾选「参照」，且「参照」不可单独取消；取消「参照」时会连带取消「更新」。
取消某模块「参照」该模块从角色权限中移除；该角色用户不再看到菜单、直接访问得到 403。
取消自己所属角色的「権限管理 = 更新」禁止。提示「自分自身が権限管理を操作できなくなるため変更できません」。
所有模块均无权限允许保存，但需在确认弹窗提示「このロールのユーザーはどの業務画面にもアクセスできなくなります」。

保存流程

  1. 点击「保存」→ 弹出影响确认：「この変更は直ちに反映され、対象 N 名（有効 M 名）の権限が変わります。」并列出变更的模块与前后差异。
  2. 确认后保存；成功后退出编辑态，矩阵与角色卡片同步刷新，显示「権限を更新しました」。
  3. 若放弃修改：「破棄」或离开页面时，如有未保存变更，二次确认「変更内容を破棄しますか？」。

结果与状态变化

  • 权限即时生效：该角色下所有用户的下一次请求按新矩阵判定，不要求重新登录。
  • 审计记录每个模块的参照/更新差异，以及受影响用户数快照。
  • 正在查看被移除模块的用户不被强制跳转，但其下一次导航或操作会得到 403；已渲染的页面内容不会追溯隐藏。

异常

  • 并发修改：保存时发现角色已被他人更新 → 提示「他のユーザーがこのロールを更新しました」，刷新为最新矩阵，当前修改需重新确认，不静默覆盖。
  • 保存失败：停留在编辑态，保留勾选状态，显示「保存に失敗しました」+「再試行」。
  • 操作中途失去权限：保存返回 403，退出编辑态并提示「権限が変更されました。画面を再読み込みしてください」。
FR-07

访问控制（导航 / 路由 / 接口）

P0 安全边界

目的

让「看不到」与「进不去」保持一致，并确保隐藏菜单不是唯一防线。

三层判定

层规则无权限时
导航 / 工作台按当前用户的角色权限过滤模块：无「参照」的模块不出现在桌面下拉、移动抽屉与工作台卡片中；某分组下全部模块无权限时，整组不显示。不可见
页面路由进入任何业务页面时在服务端校验该模块「参照」权限；进入写操作页面或执行写操作时校验「更新」。渲染 403 页面（HTTP 403），不返回任何业务数据
接口 / Server Action每个受保护接口在服务端执行同一矩阵判定，不信任前端传入的角色或权限。HTTP 403，错误码 E_FORBIDDEN，响应体不含业务数据

403 页面

  • 标题「アクセス権限がありません」，说明「このページを表示する権限がありません。管理者にお問い合わせください。」
  • 提供「ダッシュボードへ戻る」；不显示导航中无权限的模块入口。
  • 不得以「重定向到登录页」代替 403：会话有效但权限不足，与未登录是两种不同状态。

判定顺序

リクエスト→ ログイン済み？→ No → /login?next=… Yes ↓
ユーザー有効？→ No → ログイン画面へ Yes ↓ 必要権限あり？→ No → 403 Yes → 表示

其他规则

  • 权限变更在同一请求边界内生效：以请求到达时的用户状态与角色权限为准。
  • 403 与 401 严格区分：403 不清理会话，不跳登录页；401 才跳登录并带回跳地址。
  • 不存在的路由仍走 404，不因权限判定改写成 403，避免泄露路由是否存在。
  • 导航过滤后若用户一个模块都无权访问，工作台显示「表示できるメニューがありません」并保留登出入口。
FR-08

操作审计

P0 记录，不含查看界面

目的

权限变更属于高风险操作，必须能回答「谁、何时、把谁的什么权限改成了什么、为什么」。

记录范围

操作必记内容
用户作成登录 ID、氏名、邮箱、部署、角色、初始状态
用户更新变更字段的前后值（未变化字段不入记录）
有效化 / 无效化前后状态、理由（无效化必填）
角色权限变更角色、逐模块的前后权限、受影响用户数快照
角色说明变更前后説明（如开放编辑）

每条记录固定包含：记录 ID、操作日時（服务端时间，JST）、操作者登录 ID 与氏名、対象種別与対象 ID、操作種別、変更内容。

规则

  • 只追加，不提供修改与删除入口；任何界面操作都不能改变历史记录。
  • 审计写入与业务写入必须同成败：记录失败时整个操作失败并提示重试，不允许「改了权限但没有记录」。
  • P0 只要求记录与内部可查；审计查看页面、筛选与导出列为 P1。
  • 保持期限、脱敏范围与外部审计对接方式未定。TBD

05

共通规则

5.1　权限判定

  • 权限一律来自「用户当前角色」→「3.2 权限矩阵」，不来自前端传参、URL、缓存中的旧角色。
  • 「更新」隐含「参照」；不存在只有更新、没有参照的合法状态。
  • 服务端判定为唯一有效判定；导航隐藏、按钮隐藏只是体验优化。
  • 权限变更在一个请求边界内生效：请求开始时读取的用户状态与角色权限，决定该请求的全部判定结果。

5.2　保护规则（不可绕过）

规则原因与表现
至少保留 1 名有效的システム管理者防止全系统失去管理员。无效化最后一名管理员时拒绝，并提示先指定继任者。
不能无效化自己避免误操作当场失去访问。按钮仍显示，点击后给出禁止提示。
不能修改自己的角色避免把自己移出权限管理。编辑自己的资料时角色选择禁用。
システム管理者角色不可编辑系统引导锁死风险的最终保险。名称、説明、权限全部只读。
不允许物理删除用户与角色权限对象会被历史数据引用；停用可逆，删除不可逆。
不能取消自己角色的「権限管理 = 更新」即便未来开放更多角色，也不允许操作者把自己锁在门外。
审计与业务同成败不允许出现无法追溯的权限变更。

5.3　并发与一致性

  • 用户编辑与角色权限编辑均使用「更新日時」做乐观锁；冲突时不静默覆盖，交由操作者确认最新值。
  • 唯一性（登录 ID、邮箱、角色名称）以服务端判定为准；前端提示只是提前反馈。
  • 状态变更以「当前状态」为前置条件：目标已是期望状态时返回幂等结果，不重复写审计。

5.4　文案、时间与展示

  • 界面文案统一日文；本文档的中文仅用于说明。
  • 日期时间统一 YYYY-MM-DD HH:mm，时区 JST；仅日期场景用 YYYY-MM-DD。
  • 状态与角色必须显示为日文标签，不暴露内部枚举值。
  • 错误提示不包含堆栈、SQL、内部服务名等实现细节。
  • 长文本（氏名、部署、邮箱）在表格中单行省略，悬停显示完整值；弹窗中完整展示。

5.5　与现有实现的差距

现状本 PRD 要求
两个页面均为「準備中」占位，无数据列表、检索、增改、状态切换、角色矩阵
导航为静态常量，所有人相同按角色过滤导航、工作台卡片与分组
守卫只判断登录态增加用户有效性与模块权限判定
无 403 页面新增 403 页面，与 401/404 区分
无用户/角色数据与审计建立权限台帐与只追加审计

本节只描述差距，不规定实现顺序与技术方案。

06

状态与流程

6.1　用户状态

有効可登录、按角色访问
── 無効化 ──▶ 理由必须 / 需确认 ◀── 有効化 ── 理由选填 / 即时恢复
無効拒绝访问、保留台帐
  • 初始状态固定为「有効」；不存在「招待中」「承認待ち」等中间态。
  • 没有「削除」终态：无效用户永久保留，可再次有效化。
  • 无效用户的角色保持不变；有效化后沿用当前角色，不恢复停用前的历史权限。

6.2　角色与权限

  • P0 只有系统预置角色，不能新建、重命名或删除；可编辑的只有説明与权限（系统管理者除外）。
  • 角色权限变更立即作用于该角色全部用户；没有生效日期与定时生效。
  • P1 引入自定义角色后，才需要定义「角色删除前必须迁移所属用户」等规则。

6.3　三条核心流程

新人授权

进入用户列表 → 新規登録 → 填登录 ID / 氏名 / 邮箱 / 部署 → 选择初始角色（默认閲覧者）→ 保存 → 对方获得对应菜单。

离职停用

检索目标 → 無効化 → 核对氏名与登录 ID → 选择理由（退職）→ 确认 → 对方下次请求被拒；台帐与历史保留。

职责调整

转岗时优先改用户角色（个体）；同类人员批量变化时改角色权限（群体）。两者都会即时生效并留下审计。

08

未决事项与假设

以下问题会改变权限模型或安全边界，需在进入实现前确认。未确认期间，本文档采用「当前处理」一列的做法。

#问题为什么重要当前处理（仮）
Q1 用户台帐与外部认证基盘，哪边是「正」？新建用户时是否校验/开通外部账号？ 可能出现「本系统有权限、但外部无账号无法登录」或「外部有账号、本系统无台帐被拒」的不一致。 本系统只存权限台帐；新建时不同步外部，登录由外部认证决定。TBD
Q2 角色数量、名称与 3.2 权限矩阵的最终取值？ 决定每个岗位实际能看到与能操作的范围，直接影响上线后的可用性。 采用四个系统角色的提案矩阵，待业务确认后固化。TBD
Q3 是否需要「一人多角色」？ 兼岗人员需要权限并集；若确定需要，用户与角色的关系、UI 与判定都要改。 P0 为 1 用户 1 角色；多角色列 P1，并以角色新建/迁移规则为前提。仮
Q4 审计日志的查看权限、保持期限、是否对接外部审计？ 影响合规与留存成本；也决定 P1 的查询与导出设计。 P0 只记录不提供界面；保持期限与访问者未定。TBD
Q5 部署候选值来自哪里？是否需要部门主数据？ 固定候选与外部主数据的同步方式不同，会影响编辑体验与数据一致性。 使用固定候选，未设定可为空。TBD
Q6 停用与权限变更是否要求「下一次请求即生效」？现有无状态会话如何满足？ 若会话只在登录时判定，离职人员可能继续访问直到会话过期，构成安全缺口。 以「下一次请求生效」为目标；实现方式与可接受延迟待技术确认。TBD
Q7 权限粒度只到「模块」是否足够？是否需要页面级或操作级？ 例如「能看请求列表但不能审批」需要更细粒度；这会改变矩阵结构与编辑界面。 P0 为模块级（参照/更新）；更细粒度暂不纳入。仮
评审重点 请优先确认 Q2（权限矩阵取值）与 Q6（即时失效），这两项决定本模块能否真正承担访问控制职责； 其余问题可在实现过程中并行确认，不阻塞原型评审。
